## 一、A1 · parseDigest 第三级容错对嵌套 rubric 整体失效

### 我的核实链

**第一反应**：这条要成立，必须同时满足两个前提——① 当前代码第三级正则还是旧版（没随 rubric 一起改）；
② rubric 输出契约真的产生了嵌套。我先读代码验证这两个前提，而不是直接跑它的脚本。

- 读 `parseDigest`（975-1011 行）：984 行 `const re = /\{[^{}]*\}/g;` 原样在——**第三级是老代码，
  v4.0.2 改契约时只动了一级/二级解析和 normScore，没人回头检查兜底路径**。
- 读 1004 行：`score: normScore(d.scores || d.score)`——嵌套 `scores:{...}` 契约坐实。

**两个前提都成立，但我仍不认「实锤」二字**——代码阅读只能证明「会断」，不能证明「断了之后
结果真的是 0 条」。所以我写了独立复现：构造「max_tokens 截断、连收尾 `]` 都没写出来」的输入，
照搬 982-989 行逻辑跑 Node。结果：**提取到 2 个对象（都是 scores 内层碎片），含有效 idx 的 0 个，
最终可解析条目为空数组**。审查者的推演一步一步全部重演成功，此时我才认账。

**为什么 112 项测试没抓到**：我 grep 了 smoke 全部 rubric 用例——它们全部构造的是
「一级 `JSON.parse` 就能成功」的输入，没有任何用例打「严重截断 + 嵌套格式」的第三级。
这正是我们自己在 4.6.8 反思过的第 1 条「测试通过但没测到东西，比测试失败更危险」的活标本，
而且这次是**外部审查者用「逐区通读 + 对新旧改动做交互推演」抓到的**，作者自查两轮都没发现。

### 修法决策（为什么是这个正则，而不是别的）

采用审查者给的 `/\{[^{}]*(?:\{[^{}]*\}[^{}]*)*\}/g`（支持一层嵌套）。我推演过它为什么对：
**截断发生在流末尾，截断点之前的完整条目括号必然配平**，新正则能把完整条目整体吃出来；
截断中途的残段括号不配平、不匹配、也不崩溃（返回空数组）。

没采用的方案：通用递归正则（任意深度嵌套）。理由：契约里只有一层嵌套（scores），
YAGNI；递归正则可读性差，而这段是三年都不会看的兜底代码——**可读性在兜底路径里比通用性重要**。
如果未来 rubric 加深嵌套，我在修复处留的注释已经指明扩展点。

配套：补 smoke 用例「entry1 完整 + entry2 截断一半 + 无 `]`」断言恢复 entry1——
把审查者指出的测试盲区钉死，防止回归。

## 二、A2 · cron 心跳键单键覆盖，削弱 v4.0.2.3 自己的目标

### 我的核实链

读 scheduled（2201-2248 行）：2220 行 `runKey(window, 'cron')` 确实只到 window 粒度，
往下 fetch/digest/send 三分支写的**同一个键**（只有值里 kind 字段不同）。

**这一条让我脸热的地方在于：它不是普通缺陷，而是观测仪器自己制造假阳性。**
v4.0.2.3 的全部意义就是区分「cron 没触发」vs「触发了但入队挂了」。但如果键是 window 级，
早班 05:40 fetch 缺席而 05:50/06:00 在场时，键依然存在——明早我若看到
`run:2026-10-27-am:cron` 存在，就会误判「cron 触发了」，然后去查消费侧，**方向从第一步就错**。
审查者说「按这个验证方法，悬案的答案恰好被自己造的观测仪器挡住」——完全准确。

### 修法决策

kind 变量本来就在 2215-2217 行算好了，拼进键名即可：`run:{window}:cron:fetch` / `:digest` / `:send`
（enqueue、cron-error 同理）。没采用的方案：另建键族或改记录结构——`runKey(window, stage)` 的
键族语义不变、RUN_TTL 不变、health 聚合不受影响，**最小侵入就是最优解**。

**时效判断**：这条必须赶在 10-27 早班前部署，否则明早验证数据作废、还得重来一班。
这也是我把它排进首批部署的原因（实际已随本次部署生效）。

**连带预期**：改键名后 smoke 里 4 处旧键断言必然变红。我没有回避，同步更新断言并
**新增「早班三触发点各写独立键」的断言**——键名是行为的一部分，测试红是锁正常生效。

## 三、B1 · A/B 采集采样偏差 + 途中岔出的「假绿」标本（本回应的重点）

### 采样偏差的核实与修法

读 `enrichMaterial`（1028-1038 行旧版）：`abExp.push` 确实被裹在 `if (md.length > desc+40)` 里。
我的理解：A/B 实验要回答「两版 desc 哪个质量好」，但采样条件是「toMarkdown 已经在长度上大胜」——
这是教科书级的选择性采样。四种情形里只有「toMarkdown 长、裸抽短」被采到，
人眼结论必然系统性偏向 toMarkdown。审查者那句「不是你度量出来它好，而是只有它好的样本被采到了」
一针见血。

修法：push 移出长度 if，只要 `got.rewriter` 存在（仅 toMarkdown 路径持有同份 HTML）就无条件记录；
两版各截 200 字，纯内存零子请求，成本核算成立。

### 然后发生了这轮修复里最有意思的事——旧测试突然红了

改完跑 smoke，**旧用例「Jina 路径无同份 HTML → 不进 A/B 采集」失败**。我的第一反应不是
「改测试让它绿」，而是分叉排查：

1. **是我把 enrichMaterial 改坏了吗？** 写了独立 dbg 脚本隔离复现：结果 Jina 场景 `ab2.length=0`
   （是对的！）——与 smoke 里的失败矛盾。**矛盾说明差异在测试环境，不在被测代码。**
2. **追查差异**：读 `createNet`，发现它签名是 `(env, budget)` **只收两个参数**，
   `get env() { return env; }` 返回的是第一个参数。而 smoke 的 `mkB1Net` 把 `JINA_KEY`
   放在**第三个参数**——从未生效过。所谓「Jina 路径」用例，**从诞生起就在跑 toMarkdown 路径**。
3. **那它为什么以前是绿的？** 继续追：ab2 和 ab1 共用同一个 `b1item` 对象，ab1 先跑把
   `b1item.desc` 改写成了 markdown 文本（约 55 字）；轮到 ab2 时
   `md.length(~55) > desc(~55)+40` 不再成立 → 旧代码不采集 → `ab2.length===0` **碰巧成立**。
   **参数丢失 + 状态污染，双重假绿。**
4. **不轻信推理，实证收尾**：用 `git archive HEAD` 把旧版代码+旧测试独立复跑——旧版确实
   112 项全绿。证明假绿是历史事实，不是我改出来的。

修复：env 合并进 `createNet` 第一个参数（JINA_KEY 真正生效）、用例改独立克隆。
现在 Jina 用例是**真过**——它测的分支终于被真正执行。

**这条的教训我写进了 DEVLOG §4.7.8**：测试断言行为之前，先确认前置条件（mock）真的生效了；
「测试红」不一定是被测代码坏了——有时是测试自己从来没测到东西，红了才暴露。
这与 A1 互为镜像：A1 是「生产兜底路径没测试覆盖」，假绿是「测试覆盖了一个不存在的路径」。
