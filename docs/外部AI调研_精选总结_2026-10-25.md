## 一、调研方法：为什么这份报告可以信

### 1.1 双线并行，交叉验证

调研分两条独立的线执行，结论互相印证：

- **线 A · GitHub 项目对标**：找「已经在生产环境解决同一问题」的开源项目，看它们怎么做
- **线 B · 学术与官方文档**：找「有实证数据支撑」的论文和厂商官方文档，看什么被证明有效

两条线都指向同一批结论时（如 rubric 打分、embedding 事件聚类），才进入建议清单；
只有一条线支持的（如个别博客的定价数据），标注为「待验证」。

### 1.2 证据分级（本报告内部的采信权重）

| 级别 | 类型 | 权重 |
|---|---|---|
| 1 | 一手论文（arXiv，有量化指标） | 最高——「实证有效」 |
| 2 | 厂商官方文档（智谱/阿里/DeepSeek/OpenAI） | 高——「平台行为的事实」 |
| 3 | 可 clone 验证的开源项目（有 star 数、有代码） | 中高——「有人这么干且干成了」 |
| 4 | 技术博客/实测 | 低——仅作线索，关键处标注「调研时点数据」 |

### 1.3 约束前置筛选

所有候选方案**先过 GUJI 的硬约束账，再谈优劣**：
免费档单次调用 50 子请求、Workers AI 每日免费神经元额度、CPU 时限、KV only。
过不了账的一律降级（如需要 Postgres 的方案直接出局——160 条/天的规模不需要它）。
这条纪律来自 DEVLOG 本身：**「先读官方 limits 再设计」**——调研同样遵守。

### 1.4 诚实声明

- 定价与延迟为**调研时点数据**，采用前以厂商最新价格页为准
- 标注「未找到可靠来源」的（如中文书名号/中英混排的专门研究）就是没找到，不编
- 本报告的所有判断都可独立验证：论文有编号、项目有仓库、文档有链接

## 二、先确认「不改什么」（为什么这步排在前面）

调研的第一步不是找新东西，是**验证现有选择**——因为「把对的改成错的」比「不改进」更糟。
四个核心选择都找到了外部依据：

| GUJI 现有设计 | 外部依据 | 判断 |
|---|---|---|
| 两步流水线（先精选后总结） | AIHOT / Horizon / Newsletter-AI 均为多步流水线 | 主流，保持 |
| 模型只回 idx、链接代码回填 | daily-briefing 同思路（「每条 URL 都来自真实搜索结果」） | **第一梯队**，保持 |
| 无思考模式（glm-4-plus） | arXiv 2512.03503：摘要任务「思考越多，忠实度越差」 | **论文级验证**，保持 |
| 三级容错解析 | 智谱/DeepSeek 官方 API 仅 json_object（保语法不保结构） | **必须保留**，保持 |

其中第三条值得多说：DEVLOG 坑 9 选 GLM 是「试错逼出来的」——Qwen3 三重开关全失效后换模型。
而论文 2512.03503 从学术侧证明了「这个选择歪打正着」：**两条独立证据链（生产事故 + 论文实证）指向同一结论**，
这是本次调研中信号最强的一条，也说明 §10 的地基不需要动。

## 三、三个差距及判断依据

### 3.1 精选标准是「提示词散文」——不可复现、不可评测

**现象**：`buildPrompt` 用自然语言描述标准（「真正重要、有实质信息量的」「跳过营销通稿、人事任命」）。
意图清晰，但「真正重要」对模型是连续光谱，每次运行的边界会漂移；对人是黑盒——读者问「为什么这条上了日报」，
除了 `aiTrace` 里的模型原文，没有可回答的结构化依据。

**证据链**：
- AIHOT（同构度最高的对标项目）把标准写成**五轴加权 rubric**：sig 份量 / nov 增量 / cred 证据 / reson 共振 / act 可用性各 0-10 分 × 内容类型固定权重（每行权重和=10，天然合成 0-100），并明列噪声上限（营销软文 sig≤2、人事招聘 sig≤2）
- G-Eval 论文（arXiv 2303.16634）：分维度 rubric + CoT 理由再出分，显著优于单一总分和「角色扮演+两步指令」（摘要任务 Spearman 0.514）
- PSA 论文（arXiv 2506.22270）：分维度 prompt 让 LLM 模仿编辑评审，与人类 Top-5 重合 75%、NDCG@5 0.95（注意：样本仅 30 篇，属初步证据——所以建议是「改造提示词」而非「推倒重来」）

**为什么是差距**：不是「现在错了」，是「现在无法变好」——没有形式化标准，就没有评测集；
没有评测集，每次改提示词都是碰运气。AIHOT 与「提示词散文」项目的分水岭正在这里。

### 3.2 事件级聚类去重缺失——「12 条里 5 条同一新闻」

**现象**：`finalizeItems` 的去重是 normTitle 精确键——同题不同表述（「OpenAI 发布 GPT-6」vs「GPT-6 正式亮相」）漏合并，
页面「×N 源」署名只在标题几乎一致时出现。

**证据链**（四个独立项目同模式，强信号）：
- AIHOT：标题+摘要向量近两周召回候选 → LLM 判 SAME_OCCURRENCE / SAME_STORY / UNRELATED →「拿不准的合并」→ 写入前复核
- 3mins.news（Workers 实战）：cosine 0.7（新闻域经验值）+ 18 小时时间门限（防「2025 地震」并入「2026 地震」）
- TensorFeed（Workers AI 免费档）：bge 系列 embedding + single-link 阈值 0.82 + 独立来源数分级佐证（1 源存疑 / 2-3 有限 / 4+ 可靠）
- newsence（Workers AI 免费档）：BGE-M3（1024 维多语言，覆盖中文）+ 0.85 阈值

**为什么是差距**：这是「日报」这个产品形态的核心体验问题——读者要的是「今天发生了什么」，
不是「同一条新闻的第 5 个转载标题」。且它是四个差距里唯一有**成熟参数可直接搬**的。

**为什么优先于 SimHash**（对审查报告 B4 的修正）：SimHash 3-token shingle 依赖词形重合，
对「同事件不同表述」召回有限（作者复核也指出了这点）；而语义向量 + 时间门限直接度量「是不是同一件事」。
且 bge-m3 一次批量调用 = 1 个子请求，Worker 内 160² 暴力算余弦无压力——**这是比 SimHash 更准且同样便宜的路**。

### 3.3 无代码级数字/专名校验——中文摘要最大幻觉源

**现象**：`parseDigest` 只校验 idx 和长度，摘要内容的数字/产品名与原文的一致性无人把关。
提示词说了「不得编造、数字名称保留原文」，但提示词是软约束。

**证据链**（三处独立数据同向）：
- SuperCLUE-Faith 2025.5：中文幻觉率 Qwen3 29%、DeepSeek R1 21%
- EBU/BBC 2025.10：3000 条 AI 摘要测试，45% 含重大问题、20% 有严重准确性问题
- 国内媒体 11 款中文 AI 新闻总结测试：76% 真假参半，开深度思考更易编（与 2512.03503 论文互证）
- 国产模型数字比较错误实测普遍（9.11 vs 9.9 难倒多数模型）

**为什么是差距**：日报的立身之本是「一手来源、不编造」。数字写错（「营收 130 亿」写成「13 亿」）
对读者是实质伤害，而对代码来说这是**零 token 成本**可防的——正则抽取 + 子集校验，整个清单里性价比最高的一项。

## 四、建议及「为什么这么做」

### P0 · 立即可做（纯提示词/代码，**零预算影响**，约半天）

**① 精选标准形式化：散文 → rubric 打分**

改成每条输出四维分数 + 一句话理由，代码排序 + 分桶取 12：

```
维度（各 1-5 分，先理由后分数）：
  影响面：对行业/市场的实际影响大小
  信息密度：包含多少可验证的新事实
  来源权威：一手官方 > 深度媒体 > 通稿
  时效性：是否新近发生/发布
```

- **为什么**：G-Eval + PSA 双论文支持「先理由后打分」；理由字段顺带解决「为什么这条上了日报」的可解释性（进 `aiTrace`，可选展示给读者）
- **为什么四维不是五轴**：AIHOT 五轴里「共振（多源报道热度）」和「可用性」依赖 GUJI 还没有的信号（跨源热度统计），先上四维，共振轴留给事件聚类落地后自然获得
- **注意**：自报分**只排序、不设绝对阈值**——arXiv 2502.15242 证明模型自报分数系统性过度自信（校准误差比内部探针高 5-38 倍）

**② 提示词加硬约束清单**（AIHOT 同款）：
产品名/数字/版本号必须原文找得到对应；宁省略不补全；相对时间照抄不换算；不得强化语气（「正在探索」≠「已经采用」）；排他性表述（「首次/唯一」）仅原文明示才保留。
- **为什么**：零成本，直接压缩编造空间；这些条目全是「模型最容易越界的地方」的经验清单

**③ 代码层数字/专名校验**：正则抽取摘要中的数字（带单位），要求为原文（标题+desc）数字集合子集；产品名若非原文子串 → 打回重写。
- **为什么**：见 3.3。零 token 成本，纯代码可实现，有测试可锁（smoke 已有 tgTruncate 式纯函数测试模式）

**④ temperature 0.3 → 0.1**。
- **为什么**：低温降编造是机制性共识（高温更易采到低概率错误 token）。「0.7→0.3 降 37%」只有博客背书、无论文——所以只调到 0.1 求稳，不宣称具体收益

### P1 · 短期（1-2 天，预算 +2~11/50）

**⑤ 事件聚类去重**：

```
finalizeItems 之后、enrich 之前：
  1. Workers AI bge-m3 批量 embedding（title+desc[:200]，160 条 1 次调用 = 1 子请求）
  2. 时间门限 48h + cosine ≥ 0.8 → 候选对
  3. v1：直接合并（「拿不准就合并」），代表稿按 完整度60%/权威25%/时效15% 选
  4. v2（可选）：仅对 0.7-0.8 边缘对调 1 次 LLM 判定 SAME_EVENT/RELATED/UNRELATED
```

- **为什么放 enrich 前**：去重后再 enrich，thin 条目更少，可能连 enrich 子请求一起省
- **为什么保留 normTitle**：精确键是零成本快路径，embedding 是第二轨，不是替换关系
- **为什么 48h 门限**：3mins.news 的 18h 是它的更新频率；GUJI 早晚两班 + 最长 30d 窗口（播客），48h 兼顾「同班合并」与「防跨月误合并」
- **预算账**：v1 = +1 子请求；v2 = +5~15。digest 班 19 → 20~34，峰值仍 ≤ 50 的 68%——符合 DEVLOG「峰值 ≤ 60% 才安全」的边缘内，若从严可只上 v1

**⑥ 模型分层**：打分/判定换 DeepSeek V4-Flash（$0.14/$0.28 每 M，<2s，约为 GLM 价 1/3）；最终写作保留 GLM 但建议 A/B 测 GLM-4.6（结构化输出更强、`thinking.type` 可关）。
- **为什么**：arXiv-digest 用 gpt-5-mini 打分 + gpt-5 写作、Horizon 文档明建议「便宜模型跑批量打分」——160 条打分是高频廉价活，12 条写作是低频质量活，分层是同类项目的共识省钱法
- **为什么不是全换 DeepSeek**：GLM 中文原生是写作质量的基本盘，摘要只有 12 条，写作侧不值得为省钱降质量

**⑦ 兜底链升级**：llama-3.1-8b → Qwen3-235B-A22B（中文自然度测评最优、权重开源），或接 cloudflare-llm-gateway（Workers 免费档九厂商 key 池自愈 + 自动故障转移）。
- **为什么**：llama 中文写作是明显短板（§10 注释自己承认「中文原生质量高于 llama」）；Qwen3-235B 便宜且中文好；网关方案解决「单点兜底」——一个厂商挂就全挂

### P2 · 中期（可选）

**⑧ MMR 多样性选择**（λ≈0.5，约 20 行）：选 12 条时减「与已选条目最大相似度」，防全挤同一主题。embedding ⑤已有，增量成本为零。
**⑨ 夜间原子句自检**（ACUEval，arXiv 2024.findings-acl.597）：摘要拆原子事实逐条对原文判是/否，忠实度 +10-23%；12 条 × 便宜模型，挂夜间空闲班次。
**⑩ 自建评测集**（AIHOT SelectBench 模式）：100-200 条人工标注「该不该上日报」样本，每次改提示词跑一遍。**这是让 rubric 长期有效的唯一机制**——也是 AIHOT 与「提示词散文」项目的真正分水岭。

## 五、克制清单：为什么明确不做

| 方案 | 不做的理由（有依据） |
|---|---|
| Chain of Density（迭代补实体） | 50 字短文用不上；token 成本 4-5 倍；CoD 论文自己警告长度压力诱发编造 |
| 多模型投票 | 成本 ×3；2512.03503 证明自洽性提升风格而非准确性 |
| Postgres/pgvector | 160 条/天，Worker 内暴力算足够；3mins.news 上 pgvector 是 10 万+/天规模的需求 |
| 自托管中文摘要小模型（mT5/BART 微调） | 与 API 模型的「25 字标题+50 字摘要+零编造」质量差距明显，且 Workers AI 不托管 |
| 反思/思维链 | 2512.03503：摘要场景思考越多忠实度越差；国内媒体实测「开深度思考更易编」 |
| 置信度绝对阈值 | 2502.15242：自报分数过度自信，只配当排序信号 |

**为什么写克制清单**：DEVLOG 坑 3 的教训是「过于复杂 = 藏着 bug」——调研的产出如果只有加法，
就是把外部世界的复杂度搬进一个免费档系统。**每一份「更好的方法」清单都应该自带「不做什么」。**
