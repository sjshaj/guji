# 从零重建指南（Bootstrap from Scratch）

> 给「拿到这个仓库想自己建一套」的人。**先读 `README.md` 快速开始**，
> 本文件只补它缺的两块：① 账号基建（KV/队列/域名的创建命令与顺序）
> ② 从零到首次运行的完整步骤与每步的自检。
>
> 全程约 1-2 小时（有 Cloudflare 经验）。免费档可跑，**唯一可能付费的是智谱 key**（见 §4）。

## 1. 前置条件

| 项 | 要求 | 没有会怎样 |
|---|---|---|
| Cloudflare 账号 | 免费档即可 | —— |
| Node.js 22+ | 本地 | 跑不了 wrangler 和测试 |
| `CF_API_TOKEN` | Workers 编辑权限（Edit Workers） | 部署不了 |
| 智谱 API key | open.bigmodel.cn 注册（glm-4-plus 有免费额度，超出付费） | **退化路径**：精选层退回 Qwen3+llama，Qwen3 空 content 病无解，digest 可能恒 0——「能跑」但「不完美」 |
| Telegram bot | @BotFather 新建（免费） | 没有推送，系统退化为纯网站 |

## 2. 账号基建（顺序不能乱）

```bash
# ① KV：先建 namespace，拿到 id
npx wrangler kv namespace create guji-free-kv
# → 输出 {"id": "xxxxxxxx...."}，记下它

# ② 改 wrangler.toml：把仓库里的 KV id 换成你自己的
#    [[kv_namespaces]] binding = "GUJI_KV" id = "你的id"

# ③ 队列：**不要手动建**！[[queues.producers/consumers]] 绑定在首次
#    wrangler deploy 时会自动创建（guji-fetch / guji-digest / guji-send / guji-dlq）
#    手动建容易与绑定语义冲突，让部署去建

# ④ 部署（自动建队列 + Worker）
cd src && CLOUDFLARE_API_TOKEN=你的token npx wrangler deploy
```

**部署后必须补一步**（这是仓库交付时踩过的最深的坑，DEVLOG §4.3 坑 12）：

```bash
# ⑤ 队列级延迟：wrangler.toml 的 producer delivery_delay 对已存在绑定不生效，
#    必须走 API 给 digest 队列设默认延迟 90 秒：
curl -X PUT "https://api.cloudflare.com/client/v4/accounts/$CF_ACCOUNT_ID/queues/$DIGEST_QUEUE_ID" \
  -H "Authorization: Bearer $CF_API_TOKEN" \
  -d '{"queue_name":"guji-digest","settings":{"delivery_delay":90,"message_retention_period":86400}}'
# 队列 ID 从 wrangler queues list 拿
```

**自检**：`npx wrangler queues list` 应看到 4 个队列；
`curl -s -X GET ".../queues/$DIGEST_QUEUE_ID"` 返回的 settings.delivery_delay 应为 90。

## 3. 域名（二选一）

**A. 免域名（最快）**：什么都不用配，wrangler deploy 后访问
`https://guji.<你的subdomain>.workers.dev`（注意：某些网络环境不可达 workers.dev，
见 DEVLOG §4.2，用 B 更稳）

**B. 自定义域名**（仓库线上用的方式，wrangler.toml 里**没有**——在 CF 网页后台配）：

1. 你的域名 NS 已指向 Cloudflare（或把 zone 加进账号）
2. CF 后台 → Workers & Pages → guji → Settings → Domains & Routes → Add
3. 填 `你的域名` + zone，保存后等证书自动签发（分钟级）
4. 验证：`curl -s https://你的域名/api/diag` 有 JSON 返回

**自检**：`curl -s "https://你的域名/api/diag"` 返回
`{"kvFound":..., "aiProbe":...}` 类 JSON = 通了。

## 4. Secrets（按需，最少配智谱）

```bash
cd src
npx wrangler secret put ZHIPU_KEY        # 强烈建议：没它精选层退化
npx wrangler secret put TG_BOT_TOKEN     # 要推送就配
npx wrangler secret put TG_CHAT_ID       # 私聊目标（你自己的 chat id）
npx wrangler secret put TG_CHANNEL       # 公开频道（@username 或 -100 数字 ID）
npx wrangler secret list                 # 自检：应看到刚才配的
```

Telegram chat id 获取：给 bot 发条消息，然后
`curl "https://api.telegram.org/bot$TOKEN/getUpdates"` 看 `result[].message.chat.id`。
频道：bot 建好后新建公开频道，把 bot **加为管理员**（必须，否则发不了消息）。

## 5. 首次运行与验收

```bash
# ① 本地测试先行（不需要任何 secret 和网络）
node src/smoke-v4.mjs && node src/e2e-v4.mjs   # 必须 17 + 39 全绿

# ② 手动触发第一班（不等 cron）
curl -s "https://你的域名/api/build" | python3 -m json.tool
# 合格：count ≥ 100（39 源），failures ≤ 3 个（源侧故障看 docs/源病历.md）

# ③ 验证延迟投递真的在（可选但推荐，方法见 DEVLOG §4.3）
#    删同 window 旧分片键 → /api/build → run:{window}:digest 的 at 比 t0 晚 90-110s

# ④ 验证推送（配了 TG 的话）
curl -s "https://你的域名/api/push"    # 返回 push 数组，ok:true
```

**然后**：cron 已按 wrangler.toml 的 4 个表达式自动跑（北京 05:40/05:50/06:00
早班、21:40/21:50/22:00 晚班），无需再配。日常验收按
`docs/首次cron验收手册.md` 执行。

## 6. 换源 / 加源

- 改 `src/index.js` §1 的 `FEEDS` 数组（一行一个源，四要素：kind/cat/win/url 或 cik）
- 同步在 `docs/源病历.md` 加一行病历（这个仓库的维护规矩，README 文档索引表）
- 重跑 smoke（有分片数量断言）+ 部署

## 7. 重建后与线上的预期差异（诚实清单）

| 差异 | 原因 | 处理 |
|---|---|---|
| 部分源抓不到 | 源故障是实时的（Lex 502、Dwarkesh 000 是源侧问题） | 查源病历的预期，别改代码 |
| 精选条数波动 | 素材池 24 条上限 + 模型判断 | 抓取量少时精选必然少 |
| 首次 AI 调用慢 | Workers AI GPU 冷启动 90s+ | 正常，AI_MS=150000 已容忍 |
| 智谱欠费后 digest=0 | 模型链全挂的降级行为 | /api/diag 看 zhipuProbe，充值或换 key |
| 免费档政策变化 | Queues 免费档 2026-02-04 才上线，未来可能调整 | 外部变量，仓库管不了；真变了按 DEVLOG §3 的方案 A/C 退化 |
