## 二、对原代码的理解（独立复盘）

以下理解全部从代码本身得出，未依赖 DEVLOG 的事后叙述——两者一致，说明文档忠实。

### 2.1 架构本质

v4 的核心洞察是：**Cloudflare 免费档单次调用 50 个子请求且第 51 个静默失败**，
所以「一个 invocation 跑全链路」必然走钢丝（v3 峰值 47/50）。v4 用 Queues 把预算**切开**：

```
cron :40 ──4 条──▶ [guji-fetch]  消费者×4 并行，每片 10 源，独立 50 预算
cron :50 ──1 条──▶ [guji-digest] 90s 延迟投递，读 4 分片 → enrich → AI 精选 → latest
cron :00 ──3 条──▶ [guji-send]   max_concurrency=1 串行保序推送
                     ↘ 重试耗尽 ▶ [guji-dlq] 记日志（不静默丢失）
```

各阶段峰值：抓取 ~16/50、精选 ~19/50、推送 ~29/50——**每段余量 ≥ 40%**。

### 2.2 设计得当的部分（先确认）

1. **§6/§7 预算网关**：所有 fetch/KV/AI/队列发送收敛到 `createNet` 单一出口，记账可审计；
   且**记账不限流**——「静默丢数据比超限报错危险」这个判断完全正确。
2. **分片键 `window+序号` 隔离 + 内容整体覆盖写**：重试幂等， digest 消费者以「分片存在」
   判断抓取完成，不被单源失败卡住。
3. **`material[idx-1]` 回填**：AI 只回 `{idx,title,summary}`，链接/来源全部回填原始数据——
   从结构上杜绝编造链接（LLM 幻觉头号重灾区）。
4. **Queues 重试参数语义化**：digest `max_retries=10`，退避充当「等抓取班完成」的等待；
   手动路径另有 90s 队列级 delay + 消费者内 45s 轮采 + 40 预算护栏三重保险。
5. **`tgTruncate` UTF-8 字节截断**：DEVLOG 坑 7 的正确修复，且有测试锁定。
6. **先精选后总结**：产品纪律同时写进 prompt 和代码，正确。

### 2.3 数据流细节（抽查验证过的点）

- `finalizeItems` 管道：时间窗过滤 → 无日期判死 → AI 关键词 → 每源限额 → arXiv 截断 →
  normTitle 合并去重（`also` 数组即页面「×N 源」署名）→ 时间倒序。
- 早晚班互补：`lastDigestAt` 存 latest KV（省一次独立 put），晚报只精选增量，
  一条新增也起一期，全无新增回退全窗口（宁薄勿空）。
- 模型链：有 ZHIPU_KEY → GLM-4-plus 主力×2 + llama 兜底×2；无 → Qwen3×2 + llama×2。
- enrich：只补 desc < 120 字的条目，ENRICH_MAX=4、串行、150KB 截断——三个数字
  对应 Error 1102 的教训，全部对得上。

## 三、发现（按优先级）

### A 级 · 正确性与可靠性（建议下一批修复）

| # | 位置 | 发现 | 建议 |
|---|---|---|---|
| A1 | `sendChunk` 1091-1118 + `consumeSend` 1403-1447 | **推送失败即静默丢弃**：单条 3 次尝试失败后仅 `console.error`，然后无条件 `msg.ack()`——消息永久退出队列。整片失败时 9 条全丢，只能等下一班 | 对 `results` 中失败项调 `msg.retry()`；按错误类型分流：timeout/429/5xx → retry，`chat not found`/`bot was blocked` 等永久错误 → ack |
| A2 | `sendChunk` 1097-1113 | **429 退避不当**：任何失败固定睡 `MSG_RETRY_MS=1000`。Telegram 429 响应体带 `parameters.retry_after`，提前重试会被更狠限流，3 次固定 1s 在真实限流下大概率全灭 | 解析 `j2.parameters?.retry_after`，按 `sleep(min(retry_after*1000+250, 30000))`；429 不计入 attempt 或单独放宽 |
| A3 | `xmlParser` 271-277 | **FXP 未设 `parseTagValue:false`**：默认开启会把纯数字文本转 number（`"0012"`→`12`），EDGAR CIK/编号类字段有中招风险 | 加 `parseTagValue:false, trimValues:true`。**不要**加 `htmlEntities:true`——`stripTags` 已做实体解码，双重解码会把 `&amp;lt;` 过度解成 `<` |
| A4 | `wrangler.toml` producer 段 | `delivery_delay = 90` 对已注册绑定不生效（DEVLOG 坑 12 已实测结论），但文件里仍留着，注释只提了 camelCase 的坑——**重建者会被误导** | 注释改为「仅对新建队列有效；生产 truth 在 CF 后台 Queues / REST API」，或删行指向重建指南 |

## 四、为什么建议更新（理由汇总）

**A 级是「原则未贯彻到底」而非新问题**：DEVLOG 自己定了「失败路径绝不静默」（坑 7 的遗产），
v4 在抓取段（run 记录）、精选段（markDigest）贯彻了，**推送段漏了**——A1 是同一原则的最后一个缺口。
A2 是平台行为知识缺口（TG 限流语义不在 DEVLOG 记录里）。A3/A4 是库/平台默认值咬人，
与 DEVLOG「先读官方 limits 再设计」同源。

**B 级全部有 DEVLOG 内部依据**：B1 直接兑现 Error 1102 的教训（「外部内容先裁剪再处理」的
更进一步——不处理）；B2/B3 是 cloudflare-rss-aggregator 被本项目吸收了一半的做法
（DEVLOG §2 只搬了并发模型，没搬条件请求和批量入队）；B4 是「多源合并」这个核心卖点的
精度升级，且明确克制在不引入 LSH 的范围内。

**C 级是给原作者 AI 的反馈**：这些残留不怪任何单次修改，怪的是**迭代过程没有「删除」这个
动作类型**。AI（包括我）的默认动作是生成与堆叠，不会主动回溯「这层防御当初为什么加、
现在还成立吗」。建议把「每次修复后检查同文件是否有失效的旧防御/注释」列入你们的流程。

**D 级是可维护性**，不紧急，但 ROADMAP 既已计划，本报告给出拆分顺序与防翻车纪律。

## 五、明确「不要改」的清单（防止为改而改）

经审查确认正确、**不建议动**的设计：

| 设计 | 位置 | 理由 |

| 先精选后总结流程纪律 | §10 | 产品灵魂，prompt 与代码双保险 |

`batch.messages[0]` 在当前配置下不是 bug——但代码与配置存在隐性耦合，建议在
两个消费者入口加一行注释说明「依赖 max_batch_size=1」。
