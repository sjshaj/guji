## §1 Cloudflare 免费套餐约束：cron 是"账号级 5 个"，不是"每 worker 1 个"

**问题**：一开始把 cron 上限理解成"每个 worker 最多 1 个 cron"，结果早期部署配不上去、还得去别的 worker 上腾配额。

**怎么理解**：后来查 Cloudflare 文档才确认——免费套餐的 Cron Trigger 上限是 **账号级 5 个**，不是"每 worker 1 个"。账号下所有 worker 共享这 5 个 cron 名额。

**怎么思考**：这直接推翻了"每个阶段用一条独立 cron"的设想。v4 已经用掉 4 条（`40,50 21`、`0 22`、`40,50 13`、`0 14`），再往里加根本加不动；而且即便能加，多条 cron 之间分钟重合会带来后面的双倍触发问题（见 §3）。

**怎么解决**：放弃"多 cron 驱动阶段"，改成 **单条每分钟 cron `* * * * *` + worker 内部自驱每日 6 个时点**（北京 05:40 / 05:50 / 06:00 / 21:40 / 21:50 / 22:00）。

**为什么这么解决**：账号级 5 个 cron 太紧，而"每分钟轮询 + 内部门闩"既零占用额外 cron 名额，又把"何时该做什么"的权威逻辑集中到代码里（而不是散在多行 toml 的 cron 表达式），更好推理、更好观测。

## §2 guji-min 的链式 bug：状态机卡死后被弃用

**问题**：第一版（内部代号 `min`）用 `selfCall` 状态机推进阶段（fetch → digest → send），但推进到 fetch 之后就卡住，写不进 `latest` KV，日报永远生成不出来。

**怎么理解**：状态机把"当前阶段"藏在隐式状态里，依赖每一步精确回写状态才能往下走。一旦某步没正确回写（或回写与读取之间存在竞态），状态机就永远停在 fetch，没有任何显式报错——典型的"静默卡死"。

**怎么思考**：这种隐式耦合在免费套餐这种"每次调用独立预算、可能被随时打断"的环境里尤其脆弱。与其修状态机，不如换范式。

**怎么解决**：**弃用 `min`**，改用更直白的"队列消息驱动"模型——每个阶段是一条队列消息，消费者处理完显式入队下一阶段。这就是 `lean` 的起点。

**为什么这么解决**：队列消息是显式的，且 Cloudflare Queues 自带退避重试 + DLQ 兜底，"阶段推进"从"靠状态机隐式维护"变成"靠消息流显式传递"，天然适配免费套餐的"每次调用独立 50 子请求预算"模型，也不会再静默卡死。

## §3 cron 双重触发导致抓取/精选翻倍（final 修的实锤 bug）

**问题**：`final` 早期 `wrangler.toml` 里同时配了 5 条 cron——4 条每日 cron（`["40,50 21 * * *", "0 22 * * *", "40,50 13 * * *", "0 14 * * *"]`）**外加**一条每分钟 `* * * * *`。结果某些班次抓取分片被抓两遍、精选也被触发两次，产出的候选/精选明显翻倍。

**怎么理解**：两套 cron 语义重叠在"分钟"维度。每分钟 cron 的本意是"worker 自驱时段"，但每日 cron 中像整点 `00` 分这种，与每分钟 cron 落在**同一分钟**，等于同一班次被入队两次。而且 v4 的 4 条每日 cron 本身在 `40/50/0` 分，和每分钟 cron 在同分钟重复入队——这是**实锤的翻倍 bug**。

**怎么思考**：要么去掉每日 cron 只留每分钟，要么去掉每分钟只留每日。结合 §1 的结论（账号级 cron 只有 5 个、且想保留"每分钟轮询 + 内部门闩"的简单模型），选前者最干净。

**怎么解决**：把 `crons` 改成**单条 `["* * * * *"]`**，所有"每天 6 时段"的判断收进 worker 的 `scheduledStage(t)`——只在 6 个时点返回 `fetch`/`digest`/`send`，其余分钟返回 `null`（不入队）。

**为什么这么解决**：单 cron + 内部门闩把"何时触发"的权威逻辑集中到代码，彻底消除"两条 cron 同分钟"再翻倍的可能；也顺带把 cron 名额占用降到 1。

## §4 delivery_delay 被 wrangler 静默忽略（架构陷阱）

**问题**：曾给 digest 队列设 `delivery_delay = 90`（让精选比抓取晚 90 秒入队，给抓取留就位时间），但线上 delay 一直是 0。

**怎么理解**：`wrangler.toml` 里 producer 的 `delivery_delay` 字段**只对"新建队列绑定"生效**；对已经存在的绑定，wrangler 会 silently 忽略（部署日志里有 `Unexpected fields` 警告，但不报错、不生效）。这是 wrangler 的坑，不是配置写错。

**怎么思考**：依赖一个"对已有绑定无效"的 toml 字段，等于把系统正确性寄托在一个不可靠的地方。而且 truth 不在 toml，而在 CF 后台 Queues 页 / REST API（`PUT /queues/{id}`）。

**怎么解决**：用 CF REST API 显式设置：
```bash
curl -X PUT "https://api.cloudflare.com/client/v4/accounts/$CF_ACCOUNT/queues/$QUEUE_ID" \
  -H "Authorization: Bearer $CF_TOKEN" \
  -d '{"queue_name":"guji-digest","settings":{"delivery_delay":90,"message_retention_period":86400}}'
```
但后续的 `lean`/`final`/`global` **不再依赖这个 delay**——改成"抓取与精选同时入队 + 消费者内部轮采等待分片就位 + 预算护栏"，delay 从"硬依赖"降级为"可选优化"。

**为什么这么解决**：把"等抓取就位"的逻辑放进消费者内部，与"队列 delay 字段是否生效"解耦，不管 toml 还是 API 怎么配，行为都确定。这也避免了"改了 toml 以为生效、其实没生效"的隐蔽事故。

## §5 队列 consumer 缺失，CF 直接拒绝部署

**问题**：worker 代码里绑定了队列，但没写对应的 consumer 处理函数，CF 部署直接报错拒绝。

**怎么理解**：Cloudflare 的部署契约是——worker 若声明了队列绑定（produce/consume），就必须有对应的入口。`queue` 消费者入口是独立的 handler，缺了就不让部署。

**怎么解决**：给每个队列（fetch / digest / send / retry / dlq）都补上对应的 consumer 处理函数，初期哪怕是空桩也要有。

**为什么这么解决**：这是 CF 的硬性校验，没有绕过的余地；补 consumer 同时也是把"每个阶段一个独立 invocation、独立 50 子请求预算"的队列架构真正落地的前提。

## §6 新增队列瞬时 10013

**问题**：部署后新增的队列报 `10013`（队列/绑定相关的瞬时错误）。

**怎么理解**：新建队列资源与 worker 绑定之间存在**最终一致性延迟**——资源刚建好，worker 这边的绑定还没完全对齐。

**怎么解决**：**重新部署一次**，让绑定补齐对齐。

**为什么这么解决**：这是一次性对齐问题，不是代码错；重部署即可，不必改代码。记录它是为了提醒：首次建队列后若报 10013，先重部署，别急着怀疑代码。

## §7 密钥名不匹配：ZHIPU_API_KEY vs ZHIPU_KEY

**问题**：一开始按习惯在代码里读 `env.ZHIPU_API_KEY`，但账号里实际的 secret 名是 `ZHIPU_KEY`。结果智谱 GLM 调用一直拿不到 key，静默降级到 CF Workers AI（弱模型）。

**怎么理解**：Cloudflare secret 的变量名是**区分大小写、必须和绑定名完全一致**的。名字差一个词，运行时就是 `undefined`，而代码里通常用 `|| fallback` 兜底，所以"看起来还能用，只是变弱了"——极难察觉。

**怎么解决**：代码统一改用 `env.ZHIPU_KEY`，与账号 secret 名对齐。

**为什么这么解决**：不对齐就永远静默降级，AI 总结质量悄悄变差却没人发现。修名字是唯一正解；也提醒后续：**secret 名以账号实际为准，别凭记忆写**。

## §8 SEC 12 个源全挂：缺 SEC_USER_AGENT

**问题**：部署后 SEC EDGAR 的 12 个源（按公司分别抓取的官方 filing）全部失败，KV 里 `failures` 飙到 13。

**怎么理解**：SEC EDGAR 官方明确要求请求头 `User-Agent` **必须含联系邮箱**（这是 SEC 的合规/礼貌政策，否则限速甚至拒绝）。脚本默认 UA 没有邮箱，直接被挡。

**怎么思考**：这不是代码 bug，是"配置缺失 + 不了解 SEC 政策"。SEC 源是严格一手来源里很重要的一块（覆盖那些 IR 站被 Cloudflare 防护挡住的硬件公司），不能丢。

**怎么解决**：通过 `wrangler secret put SEC_USER_AGENT` 设成 `GUJI AI Digest (bbcd75@outlook.com)`，重新跑后 `failures` 从 13 降到 1。

**为什么这么解决**：SEC 的 UA 政策是硬门槛，只能从配置满足，没法绕过；用带邮箱的真实 UA 既合规又能拿到数据。

## §9 重大事件提醒单发（final 修的实锤 bug）

**问题**：`sendMajorAlert` 里写的是 `const chat = env.TG_CHAT_ID || env.TG_CHANNEL;` —— 用了 `||` 的"二选一"语义，结果只发到私聊**或**频道其中一个，与日报"私聊 + 频道双发"不一致。

**怎么理解**：这是典型的"单目标"写法误用到"双目标"场景。`||` 只会返回第一个真值，另一个目标直接被忽略。重大事件提醒是最不该漏的，单发会让一半受众看不到。

**怎么解决**：改成双发——
```js
const chats = [env.TG_CHAT_ID, env.TG_CHANNEL].filter(Boolean);
for (const chat of chats) { /* 逐目标发送 */ }
```

**为什么这么解决**：重大事件提醒必须和日报保持一致的双发覆盖；用数组 + `filter(Boolean)` + 循环，天然支持"有哪几个目标就发哪几个"，比 `||` 正确也更通用。

## §10 每小时误触发（global 修）

**问题**：`final` 改单 cron 后，worker 每分钟都进 `scheduled`，虽然只在 6 个时点入队、其余返回 null，但**每分钟都跑一次 cron invocation**（消耗配额、产生日志噪声），而且一旦 `scheduledStage` 的分钟判断写得不够严，非时点分钟也可能误入队。

**怎么理解**：单 cron 把"所有分钟"都交给 worker 判断，判断逻辑的严谨性成了唯一防线。一旦条件松懈，"每小时误触发"就会复现抓取/精选翻倍（§3 的同一种病，只是诱因不同）。

**怎么解决**（落到 `global`）：`scheduledStage(t)` 加 **小时条件 + 阶段去重门闩（latch）**，仅 6 个时点返回 `fetch`/`digest`/`send`，其余返回 `null`；同时 `isPotentialMajor` 收窄模型调用（只在确有嫌疑时才调 LLM 判重大），并加**逐目标投递账本**避免同一提醒重复推。

**为什么这么解决**：把"触发权威"进一步收紧——既省掉每分钟无谓的 invocation，又从根上杜绝非时点分钟误入队。收窄 LLM 调用和加投递账本则是为了省钱（免费套餐 AI 调用也有限额）和防刷屏。

## §11 pm 推送"以为没发"的误判（诊断乌龙，值得记一笔）

**问题**：本会话我想确认 pm 日报是否真的送达 Telegram，去 KV 查 `push-private` / `push-channel` 时，**错误地用 `runId` 当 key 去查**，而这两个记录实际是用 `window`（`2026-10-27-pm`）写的，于是查到 `key not found`，我一度误判"pm 没推送成功、需要重推"。

**怎么理解（反思）**：这是**我读数据的低级错误**——KV 里 `runId` 级 key 和 `window` 级 key 是两个命名空间，混用就查不到。实际 pm 已 `9/9` 双发成功（`errors: []`）。

**怎么解决**：用正确的 key（window 级）重查，确认已送达；并核实那次手滑发出的 `force` 重推指令因为 curl 在用户打断时已被中断、没真正入队，所以**没有造成重复推送**。

**为什么记下来**：这是一个"以为出问题、实际没问题"的典型误判。写进思考链提醒后续接手者——**下结论前先确认自己查的 key 对不对**；也说明 KV 里 `runId` 级与 `window` 级记录并存，查询前要看清命名，否则会被自己的错误查询误导。

## §12 部署/提交层面的环境坑（本会话）

这些不是业务 bug，但卡了我们一阵，记下来让后来者少走弯路：

- **沙箱网络**：`*.workers.dev` 被沙箱屏蔽，无法直接 curl 线上 worker；`api.cloudflare.com` 可达；`github.com` 的 **git 协议（443）不通**，但 **REST API（`api.github.com`）可达**。所以本次提交走 GitHub REST API（Git Data API：blob → tree → commit → ref），而不是 `git clone` / `git push`。
- **CF token 明文暴露**：对话历史里出现过 Cloudflare API token，**按泄露处理**——应轮换（`wrangler login` 或后台重置），不要继续用旧 token。
- **队列 REST API 消息格式**：队列 `messages` 端点要求顶层 `body` 且消息体走字符串序列化，与 worker 内 `msg.body` 期望的对象结构不同，直接发容易让 consumer 解析失败。所以最终走 worker 自身 HTTP 入口（`/api/build`、`/api/push`）而非裸队列 API。
- **wrangler dev --remote 不支持 Queues**：想在本地远程触发队列消费的路子走不通，确认后放弃。

## §13 提交约定（本目录如何进仓库）

- 直接提交到 `main`（仓库惯例：自己的改动直接 push，外部审查才走 PR）。
- commit message 用中文 + 前缀（版本号 / `docs:` / `fix:`），对齐根仓库风格。
- **三版顺序提交**：`lean` → `final` → **`global` 最后**，使 `global` 成为最新提交、一眼可辨为线上版。
- 密钥已扫描：三版代码均无硬编码 token，均经 `wrangler secret put` 注入。
